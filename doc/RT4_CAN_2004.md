# PSA CAN 2004 (AEE2004) Comfort / Infotainment Bus Protocol Specification
## Reverse Engineered from Magneti Marelli RT4 (NaviDrive / RT3ev) Firmware (SW 8.31)

---

## 1. System Architecture & Hardware Target

### Vehicle & Bus Architecture
- **Protocol:** PSA CAN 2004 (Architecture Électrique Électronique 2004 - AEE2004).
- **Network Domain:** CAN CONF (CAN Confort) / Infotainment bus.
- **Baudrate:** 125 kbps (Fault-Tolerant Low-Speed CAN, ISO 11898-3 / High-Speed CAN transceiver in Comfort network).
- **Identifier Format:** 11-bit Standard Identifiers (CAN 2.0A).
- **Frame Length:** Up to 8 bytes (DLC = 0 to 8).

### Head Unit Hardware & Operating System
- **ECU Model:** Magneti Marelli RT4 / RT3ev (PSA Peugeot 407, 307, 607, 807, Citroën C4, C5, C6, C8).
- **Processor:** Motorola / Freescale PowerPC 32-bit Big-Endian (MPC5200 family / e300 core).
- **CAN Controller:** Integrated MSCAN (Motorola Scalable CAN Controller) on MPC5200.
- **Operating System:** Wind River VxWorks 5.5.1 (Tornado 2.2 / GCC 2.96 PowerPC cross-compiler).
- **Firmware Binary Modules:**
  - `Fp_Network_CAN.out`: Primary CAN network stack, transport, presentation, and application BCM bindings.
  - `bcm_hifi.out`: Audio amplifier, equalizer, volume control, and radio tuner processing.
  - `bcm_t2bf.out`: Telematics / Bluetooth / Handsfree audio server.
  - `mmi_trip.out`, `mmi_airc.out`, `mmi_alerts.out`, `mmi_tuner.out`: User interface presentation handlers.

### Protocol Stack Hierarchy
1. **Physical & Driver Layer (`C_BCM_CAN_DRIVER`):**
   - Direct MSCAN hardware abstraction (`MOTMSCAN_*`, `WNCAN_*`).
   - Interrupt service routine `ISRCallBack__16C_BCM_CAN_DRIVER` handles frame transmission and reception FIFOs.
2. **Transport Layer (`C_NETWORK_TRANSPORT`):**
   - Handles Periodic frames (`Reception_Periodic_Frame_Treatment`), Single frames (`Reception_SF_Frame_Treatment`), First frames (`Reception_FF_Frame_Treatment`), Consecutive frames (`Reception_CF_Frame_Treatment`), and Flow Control (`Reception_FC_Frame_Treatment`).
   - Supports segmented diagnostic and journal sessions (up to 21+ bytes) using PSA transport protocols.
   - Manages node absence and presence timeouts (`Supervision_Node_Presence_Treatment`, `Supervision_Node_Absence_Treatment`).
3. **Presentation Layer (`C_NETWORK_PRESENTATION`):**
   - Dispatches received message payloads to application structures in `Network_Event_Task__22C_NETWORK_PRESENTATION`.
   - Maintains previous state buffers (`Reception_Default_Values_Tab` and internal shared memory) to detect value transitions and trigger asynchronous events (`VAN_CHANGED_*`, `EVT_BCM_NET_*`).
4. **Application Interface Layer (`C_BCM_CAN` & `C_VAN_BM`):**
   - Provides public getters/setters (`get_ext_temp`, `get_trip_data_1`, `get_wheel_status`, `set_airc_command`, `set_audio_settings`, etc.) consumed by RT4 graphics engines and business logic modules.

## 3. CAN 2004 Emission Frame Matrix (RT4 Outputs)

In RT4 firmware, vehicle network transmission is strictly centralized inside `Fp_Network_CAN.out`. The physical emission dispatch table `Emission_Id_Tab` (offset `0x648A`) defines exactly 5 primary vehicle CAN emissions.

### 3.1 Primary Vehicle CAN Emissions (`Emission_Id_Tab` in `Fp_Network_CAN.out`)

| Code (`r25`) | CAN ID | Length (DLC) | Period (ms) | Target Node | Handler Function | Canonical PSA Name / Description |
|---|---|---|---|---|---|---|
| 0x00 | `0x0A9` | 8 bytes | 100 ms | Cluster / VTH | `format_nav_dashboard_infos__9C_BCM_CAN` | `MSG_RAPPEL_NAV_VTH` — Instrument cluster navigation matrix repeat (Picto ID, GPS Altitude, Distances, ETA) |
| 0x01 | `0x664` | 8 bytes | Event | Diagbox / Tester | `cmd_diag__9C_BCM_CANUcPUc` | `MSG_DIAG_SYSTEME_TELEMATIQUE_REPONSE` — Telematics KWP2000 diagnostic response |
| 0x02 | `0x229` | 8 bytes (Seg) | Event | Cluster / VTH | `set_nav_street_name__9C_BCM_CAN` | `MSG_NOM_RUE_NAV` — Current / next navigation maneuver street name (segmented ASCII) |
| 0x03 | `0x664` | 8 bytes | Event | Diagbox / Tester | `cmd_diag__9C_BCM_CANUcPUc` | Secondary diagnostic session response |
| 0x04 | `0x4A4` | 8 bytes | 255 ms / Event | BSI / Cluster | `cmd_send_failure__9C_BCM_CANP19type_diag_fail_info` | `EVENEMENT_DEFAUT_BTEL` — Telematics internal failure / DTC error state broadcast |

### 3.2 Auxiliary Bus Emissions (Hardware Dependent)

| CAN ID | Length (DLC) | Period (ms) | Target Node | Handler Function | Description |
|---|---|---|---|---|---|
| `0x1D0` | 7 bytes | 100 ms / Event | Climate ECU / BSI | `set_airc_command__9C_BCM_CAN` | Climate control panel user demands (target temps, fan speed, air distribution) |
| `0x1E5` | 7 bytes | 250 ms / Event | JBL Digital HiFi Amp | `set_audio_settings__9C_BCM_CAN` | Volume & equalization commands sent to external JBL CAN amplifier (if equipped) |

### 3.3 Internal Front Panel IPC vs. Vehicle CAN Broadcasts

On simpler head units like the **RD4**, the radio unit broadcasts radio display frames (`0x165`, `0x1A5`, `0x225`, `0x265`, `0x2A5`, `0x0A4`, `0x125`) onto the vehicle CAN bus to drive an external monochrome multifunction display (EMF-C).

On the **RT4**, the color LCD is integrated and driven directly by the internal graphics processor over the video harness. In RT4 firmware (`bcm_hifi.out`, `bcm_cdaudio.out`), audio and media states are routed to the **internal Front Panel IPC** via `C_BCM_FP_PROTOCOL` (`write__5C_KEYUcPUcUc`) and are **NOT** emitted onto the vehicle CAN network.

> [!IMPORTANT]
> **Signals Not Emitted by RT4:**
> - **Steering Stalk (`0x21F`):** This is an **input** to RT4 from the steering column switch module (COM2000), not an emission.
> - **VIN Frames (`0x336`, `0x3B6`, `0x2B6`):** RT4 does **never emit** VIN frames. The BSI broadcasts VIN onto the bus, and RT4 only listens to `0x2B6` (`MSG_VIN_VIS`) to verify against internal EEPROM to suppress its anti-theft alert.

## 4. In-Depth CAN Frame Specifications & Decoded Signals

### 4.1 Drivetrain, Electrical & Vehicle Status

#### `0x036` — BSI Power Management & Backlight Status (`MSG_COMMANDES_BSI`)
**Period:** 50 ms  
**Direction:** BSI -> RT4 / EMF  
**Length:** 8 bytes  
**Producer / Handler Function:** `Network_Event_Task__22C_NETWORK_PRESENTATION` (Case 02, offset `0x16CD8`)

Controls system power transitions, dashboard illumination, rheostat dimmer level, and Day/Night display switching.

| Byte | Bits | Signal Name | Scaling / Formula | Invalid / Default | Description & Values |
|---|---|---|---|---|---|
| 0 | 7:0 | STATUS_BSI_0 | raw | 0x0E | BSI internal supervisor state |
| 1 | 7:0 | STATUS_BSI_1 | raw | 0x00 | Reserved / sleep timing |
| 2 | 7:0 | STATUS_BSI_2 | raw | 0x00 | Network heartbeat counter |
| 3 | 7:4 | RHEOSTAT_LEVEL | raw (0..15) | 0x0 | Dashboard illumination dimmer level (0 = dark, 15 = max brightness) |
| 3 | 3:0 | ILLUM_FLAGS | bitfield | 0x8 | Bit 3: Cluster backlighting active; Bit 2: Night palette enable |
| 4 | 7:4 | POWER_MODE | enum | 0x0 | 0=Key Off / Sleep, 1=ACC (Accessories / +CAN), 2=Ignition (+APC), 5=Engine running |
| 4 | 3:0 | DAY_NIGHT_MODE | enum | 0x1 | 0=Night mode, 1=Day mode, 2=Auto (light sensor controlled) |
| 5 | 7:0 | ECONOMY_MODE | enum | 0x00 | 0=Normal, 1=Economy mode active (disable high power consumers) |
| 6-7 | 15:0 | RESERVED | raw | 0x00A0 | Reserved status bits |

### Value Tables & Bit Flags
- **POWER_MODE (Byte 4 [7:4]):**
  - `0x0`: Stop / Park / Sleep
  - `0x1`: +ACCESSORY (Key in position 1)
  - `0x2`: +IGNITION (+APC, Key in position 2, dash indicators lit)
  - `0x5`: Engine Running (+Demarrage complete)
- **DAY_NIGHT_MODE (Byte 4 [3:0]):**
  - Triggers event `BM_NET_VALID_DAY_NIGHT` in RT4 graphics engine to switch UI palette between daytime high-contrast and nighttime orange/amber dimmed theme.

#### `0x0B6` — Vehicle Speed & Powertrain Dynamic Status
**Period:** 25 ms  
**Direction:** BSI / ABS -> All Nodes  
**Length:** 7 or 8 bytes  
**Producer / Handler Function:** `Network_Event_Task__22C_NETWORK_PRESENTATION` (Case 11, offset `0x179E4`)

Broadcasts instantaneous vehicle road speed and engine crankshaft dynamic status to all vehicle ECUs.

| Byte | Bits | Signal Name | Scaling / Formula | Invalid / Default | Description & Values |
|---|---|---|---|---|---|
| 0-1 | 15:3 | ENGINE_RPM | `raw >> 3` (or raw / 8 rpm) | 0xFFFF | Crankshaft speed (13-bit unsigned int); e.g., `0xD900 >> 3` = 6,944 RPM |
| 0-1 | 2:0 | RPM_STATUS | bitfield | 0x0 | Engine run / crank status flags |
| 2-3 | 15:0 | VEHICLE_SPEED | `raw * 0.01 km/h` | 0xFFFF | Instantaneous vehicle speed; e.g., `0x2710` = 100.00 km/h |
| 4 | 7:0 | POWERTRAIN_STATE | bitfield | 0x00 | Clutch state, brake pedal switch status |
| 5 | 7:4 | GEARBOX_POSITION | enum | 0x0 | 0=Neutral, 1=1st, 2=2nd, 3=3rd, 4=4th, 5=5th, 6=6th, 7=Reverse |
| 5 | 3:0 | ESP_CRUISE_STATUS | bitfield | 0x0 | Cruise control / limiter intervention active |
| 6 | 7:0 | RESERVED | raw | 0x00 / 0xFF | Unused / reserved status byte |
| 7 | 7:0 | CHECKSUM_COUNTER | counter / flags | 0xD0 / 0xA0 | Rolling message counter (low nibble) and status flag |

### RT4 Firmware Behavior & Disassembly Ground Truth
In older documentation, a decompiled speed parsing snippet (`(data[0] << 8) | data[1]; * 0.01f`) was erroneously assumed. Direct disassembly of `Fp_Network_CAN.out` proves that:
1. **Zero Arithmetic / Float Instructions:** There are no floating-point instructions anywhere in `Fp_Network_CAN.out`, and no register byte-extraction on `0x0B6`.
2. **Opaque Buffer Cache:** At address `0x179E4` (Case 11), the frame pointer at `r1 + 18` is passed directly to `memcmp` and `memcpy` into `this->history_cache_ptrs[11]` as an opaque 7-byte block:
   ```assembly
   17a08:   addi    r29, r1, 18     # r29 = &frame[0]
   17a0c:   bl      memcmp          # Compare with previous frame
   17a2c:   bl      memcpy          # Cache new raw payload
   ```
3. **Empty Getter Stub:** The public query function `get_filtered_speed__9C_BCM_CANPc` (offset `0x0000F7B4`) is a non-functional dummy stub returning 0:
   ```assembly
   0000f7b4 <get_filtered_speed__9C_BCM_CANPc>:
       38 60 00 00     li      r3,0
       4e 80 00 20     blr
   ```
4. **Why RT4 Ignores `0x0B6`:** As a dedicated navigation unit, RT4 derives its vehicle speed directly from GPS Doppler data, supplemented by ABS wheel encoder ticks (`0x0E6`) and reverse gear status (`0x0F6`) for tunnel dead reckoning.

### Bus Capture Proof (`dump_real_car.csv`)
- **Stationary / Idle:** `00 00 00 00 00 FF 00 A0` (0 RPM, 0.00 km/h)
- **High Rev Burst:** `D9 00 65 8F 00 FF 00 A0`
  - Bytes 0–1: `0xD900 >> 3` = **6,944 RPM**
  - Bytes 2–3: `0x658F` (25,999) $\times 0.01$ = **259.99 km/h**
  - Byte 7: `0xA0` (rolling counter / validity)

#### `0x0E6` — ABS Wheel Pulse Counters & Dead Reckoning (`MSG_IS_DAT_ABR`)
**Period:** 50 ms  
**Direction:** ABS / ESP ECU -> RT4  
**Length:** 5 bytes  
**Producer / Handler Function:** `Network_Event_Task__22C_NETWORK_PRESENTATION` (Case 06, offset `0x160F8`, trace `0x16380-0x16428`)

Provides rear wheel rotational encoder tick counters directly to the navigation computer (`t_bcm_net_dr_data`) to perform dead reckoning positional calculation when GPS satellite visibility is lost (e.g., inside tunnels or underground parking).

| Byte | Bits | Signal Name | Scaling / Formula | Invalid / Default | Description & Values |
|---|---|---|---|---|---|
| 0 | 7:0 | STATUS_ABR | bitfield | 0x00 | Bit 7: ABS active; Bit 6: ESP active; Bit 0: DR valid |
| 1-2 | 15 | REAR_RIGHT_VALID | boolean | 1 | 0 = Valid measurement, 1 = Invalid / Error |
| 1-2 | 14:0 | CMPT_TOPARD | raw integer (ticks) | 0x7FFF | Rear Right wheel pulse counter (Compteur Top ARD, modulo counter) |
| 3-4 | 15 | REAR_LEFT_VALID | boolean | 1 | 0 = Valid measurement, 1 = Invalid / Error |
| 3-4 | 14:0 | CMPT_TOP_ARG | raw integer (ticks) | 0x7FFF | Rear Left wheel pulse counter (Compteur Top ARG, modulo counter) |

### Value Tables & Bit Flags
- **Wheel Tick Counting:**
  - Standard PSA wheel encoder produces 48 or 96 pulses per wheel revolution.
  - Direction of rotation is correlated with Reverse Gear flag from `0x0F6` (Byte 7, Bit 7).

#### `0x0F6` — BSI Slow Telemetry, Coolant Temp, External Temp & Odometer (`MSG_DONNEES_BSI_LENTES`)
**Period:** 250 ms (or Event-driven on state change)  
**Direction:** BSI -> RT4  
**Length:** 8 bytes  
**Producer / Handler Function:** `get_ext_temp__9C_BCM_CANP13type_ext_temp` (offset `0x0F374`), `get_alarm_engine_info__9C_BCM_CANPUc` (offset `0x00F230`) & `Network_Event_Task` (Case 29, offset `0x16DEC`)

Contains slow-changing vehicle telemetry including engine coolant temperature, cumulative vehicle mileage, ambient temperature sensor readings, reverse gear engagement, and vehicle architectural type.

| Byte | Bits | Signal Name | Scaling / Formula | Invalid / Default | Description & Values |
|---|---|---|---|---|---|
| 0 | 7:0 | SYSTEM_STATUS | bitfield (`andi 0x1B`) | 0x88 | Vehicle electrical status and network sleep readiness |
| 1 | 7:0 | COOLANT_TEMP | raw - 40 °C | 0xFF | Engine coolant water temperature (`TEAU`); drives dash coolant gauge |
| 2-4 | 23:0 | TOTAL_ODOMETER | raw × 0.1 km (or raw km) | 0xFFFFFF | Cumulative vehicle total mileage (24-bit big endian integer) |
| 5 | 7:0 | INST_EXT_TEMP | raw × 0.5 - 40 °C | 0xFF | Instantaneous ambient temperature sensor reading |
| 6 | 7:0 | FILTERED_EXT_TEMP | raw × 0.5 - 40 °C | 0xFF | Filtered ambient air temperature for display dampening & ice alert |
| 7 | 7 | REVERSE_GEAR | boolean | 0 | 1 = Reverse gear engaged, 0 = Neutral / Forward gear |
| 7 | 6:4 | VEHICLE_DIR_TYPE | enum | 0x2 | Vehicle direction / steering geometry type |
| 7 | 3:0 | RESERVED | raw | 0x0 | Reserved bits |

### Value Tables & Bit Flags
- **Coolant Temperature Formula (`COOLANT_TEMP`, Byte 1):**
  $$\text{Coolant Temp }(^\circ\text{C}) = \text{raw} - 40$$
  - `0x28` (40): $0\ ^\circ\text{C}$
  - `0x82` (130): $90\ ^\circ\text{C}$ (Normal engine operating temperature)
  - `0x96` (150): $110\ ^\circ\text{C}$ (Engine overheat threshold)
  - Disassembly log in `get_alarm_engine_info` confirms canonical symbol: `"Get_alarm_engine_info -> DONNEES_BSI_LENTES[TEAU] =  %x \n"`.
  - In `mmi_trip.out` (`0x000054F8`, `SetPropFor_NIO_TRIP_F41_Z0_3_Temp_water`), this value directly drives the instrument cluster water temperature dial.
- **External Temperature Formula (`FILTERED_EXT_TEMP`, Byte 6):**
  $$\text{Temperature }(^\circ\text{C}) = (\text{raw} - 80) \times 0.5 = \text{raw} \times 0.5 - 40.0$$
  - `0xFF` (255): Invalid / sensor fault (`VAN_INVALID_EXT_TEMP`)
  - `0x50` (80): $0.0\ ^\circ\text{C}$
  - `0x5C` (92): $+6.0\ ^\circ\text{C}$ (Captured in `clean_start.csv`)
  - `0x6F` (111): $+15.5\ ^\circ\text{C}$ (Captured in `workbench_radio_band_change.csv`)
  - Values $\le 0x4F$ (79, $\le -0.5\ ^\circ\text{C}$) trigger ice warning flag (`type_ext_temp.ice_alert = 1`).
- **REVERSE_GEAR (Byte 7 [7]):**
  - Extracted as `(frame[7] >> 7) & 1`.
  - When transitioning from 0 to 1, fires event `VAN_FIRST_RGEAR` to automatically switch the RT4 screen to parking assistance camera or radar graphic display.

#### `0x2B6`, `0x336`, `0x3B6` — Vehicle Identification Number (VIN / VIS)
**Period:** 500–1000 ms (Periodic heartbeat)  
**Direction:** BSI -> All ECUs (RT4 is a Receiver)  
**Length:** 3 × 8 bytes  
**Producer / Handler Function:** `get_diag_VIN__9C_BCM_CANP13type_diag_vin` (offset `0x0118EC`) & Case 18 (`0x16B00`) in `Fp_Network_CAN.out`

The BSI broadcasts the 17-character ISO 3779 Vehicle Identification Number (VIN) across three sequential frames:
- **`0x336` (Part 1 - WMI / World Manufacturer Identifier):** ASCII "VF3..." (Peugeot Automobiles France)
- **`0x3B6` (Part 2 - VDS / Vehicle Descriptor Section):** ASCII "6JRH48..." (Peugeot 407 Saloon, 2.0 HDi)
- **`0x2B6` (Part 3 - VIS / Vehicle Identifier Section):** ASCII "21715383" (Sequential production chassis serial number)

### Anti-Theft Verification in RT4 (`bcm_system.out`)
RT4 **never transmits** VIN frames. Instead, `VinStateAction` at address `0x000012B8` in `bcm_system.out` performs chassis theft protection:
1. Calls `GetDiagVINnumber` (`0x00001558`) to fetch the 17-character VIN stored in internal EEPROM NVRAM.
2. Calls `get_diag_VIN` (`0x0000156C`) to read the 8-byte VIS received over CAN `0x2B6` from the BSI.
3. Compares characters 9 to 16 in a loop (`0x000015C0` - `0x00001600`).
4. If `0x2B6` is missing or does not match the telecoded EEPROM VIN, RT4 enters an unauthorized anti-theft state and sounds a loud periodic beep through the speakers.
5. In bench simulation, transmitting `0x2B6` with matching chassis digits is required to silence the anti-theft beep.

## 5. Diagnostic & Telecoding Protocol (`0x764` / `0x664`)

- **Diagnostic Request ID (Tester/Diagbox -> RT4):** `0x764` (Standard PSA Diag ID)
- **Diagnostic Response ID (RT4 -> Tester/Diagbox):** `0x664`
- **Protocol:** KWP2000 on CAN / ISO 15765-2 (UDS compatible).
- **Physical Handlers:** `Reception_SF_Frame_Treatment` & `cmd_diag__9C_BCM_CANUcPUc` (offset `0x011170`).
- **Standard Supported Services:**
  - `0x10`: Diagnostic Session Control (`0x81` Standard, `0x85` Programming, `0x86` EOL/Telecoding)
  - `0x1A`: Read ECU Identification / Software Version (CD Ver 8.31, Bootrom version)
  - `0x21`: Read Data By Local Identifier (VIN, Configuration options, HW version)
  - `0x3B`: Write Data By Local Identifier (Telecoding VIN, screen resolution, amplifier presence)

## 6. Practical Implementation & Verification Guide

When implementing an aftermarket CAN transceiver, Arduino/ESP32 emulator, or reverse-engineering toolchain (such as `python-can` or `cantools` with a `.dbc` file), observe the following electrical and timing rules:

1. **Keepalive Wakeup Sequence:**
   - Transmit `0x036` every 50 ms with Byte 4 set to `0x12` or `0x15` to prevent RT4 from entering Economy Mode or sleep shutdown.
2. **Anti-Theft Beep Suppression:**
   - Broadcast `0x2B6` (`MSG_VIN_VIS`) every 500–1000 ms containing the 8-character ASCII VIS serial number matching the RT4 unit's internal EEPROM to silence the anti-theft audio chime.
3. **Screen Climate Overlay Trigger:**
   - Transmit `0x1E3` at 100 ms to update climate graphics, temperature setpoints, and fan animation.
